\section{Introduction}
Three-dimensional scene reconstruction is a fundamental problem in computer vision. It supports applications such as augmented reality, robotics, digital twins, indoor mapping, visual localization, and 3D content creation. Classical reconstruction pipelines usually require many images, calibrated cameras, reliable pose estimation, feature matching, structure-from-motion, and multi-view stereo. Although these systems can produce high-quality geometry, they are difficult to deploy when only a small number of ordinary RGB images are available.

In practical settings, the input is often sparse. A user may only have three to five images of an indoor scene, captured by a standard phone camera. These images usually contain RGB appearance only. They do not provide measured depth maps, camera intrinsics, or camera poses. If a reconstruction system requires depth at inference time, it becomes tied to RGB-D cameras, LiDAR devices, or specialized scanning setups. This requirement is not compatible with most everyday image collections.

Recent feed-forward reconstruction models such as \mvdp{} reduce this dependency by reconstructing 3D scenes from multiple unposed RGB views. \mvdp{} is designed for sparse multi-view RGB input and directly predicts pixel-aligned 3D pointmaps without requiring camera poses or depth maps during inference. The official project describes \mvdp{} as a model that reconstructs large scenes from multiple unposed RGB views, and the CVPR paper introduces cross-reference-view blocks to improve robustness with respect to reference-view selection \cite{mvdust3r_project,mvdust3r_paper}. This makes \mvdp{} a suitable backbone for sparse-view RGB-only reconstruction.

However, RGB-only reconstruction remains difficult. Appearance alone is often insufficient for metric depth recovery in low-texture areas, occluded regions, repeated structures, and low-overlap views. Monocular depth estimation is also inherently ambiguous because a single image loses metric scale under perspective projection. Therefore, an RGB-only reconstruction backbone may generate visually plausible candidate points that are still geometrically misaligned.

This project addresses the problem by combining RGB-only multi-view reconstruction with estimated depth. The dataset may contain RGB-D frames, but measured depth is not used as an inference-time input. Instead, measured depth is used to fine-tune a monocular depth estimator. At deployment time, the system receives only sparse RGB views. The fine-tuned depth estimator predicts pseudo-depth maps from these RGB images, and the estimated depths are then used to correct the candidate point cloud produced by \mvdp{}.

The main motivation is practical deployment. The project aims to use RGB-D training data while preserving an RGB-only inference contract. In other words, depth maps in the dataset teach geometric priors to the model, while the final system does not require the user to provide measured depth.

The main contributions of this report are:
\begin{enumerate}[leftmargin=1.2cm]
    \item It defines a sparse-view RGB-only reconstruction setting in which measured depth is used for training and evaluation, but not as an inference-time input.
    \item It proposes a pipeline that combines \mvdp{} with a fine-tuned monocular depth estimator.
    \item It describes an estimated-depth correction module that refines candidate geometry produced by the multi-view backbone.
    \item It reports both depth-estimation quality and 3D point-cloud reconstruction metrics using the project experiment history.
\end{enumerate}

\section{Background and Related Work}
This section reviews three related directions: sparse-view RGB-only reconstruction, monocular depth estimation, and depth-assisted 3D reconstruction. These areas motivate the design of the proposed pipeline.

\subsection{Sparse-View RGB-Only 3D Reconstruction}
Traditional multi-view reconstruction is usually implemented as a multi-stage pipeline consisting of feature detection, feature matching, camera pose estimation, triangulation, bundle adjustment, and dense multi-view stereo. This modular design is interpretable and has been validated in many practical systems. However, each stage depends on the quality of previous stages, so errors can accumulate. These systems also typically require sufficient view overlap, reliable intrinsics, and accurate camera poses.

Recent learning-based methods move toward direct reconstruction from unposed RGB images. DUSt3R predicts 3D pointmaps from pairs of RGB images without known camera intrinsics or poses, and MASt3R extends this direction with dense matching grounded in 3D representations \cite{dust3r_paper,mast3r_paper}. When more than two images are used, pairwise methods must construct many local reconstructions and then align them through global optimization. The \mvdp{} paper notes that pairwise reconstructions may contain matching or geometric errors, and that global optimization cannot always remove these errors \cite{mvdust3r_paper}.

\mvd{} handles multiple views in a single feed-forward pass. Instead of exchanging information only between two images, it uses multi-view decoder blocks so that each view can receive information from all other views. \mvdp{} further improves stability by using multiple reference views and cross-reference-view blocks, allowing the model to fuse information across different reference choices \cite{mvdust3r_paper}.

In this project, \mvdp{} is used as the RGB-only multi-view reconstruction backbone. It produces the initial point cloud from a small number of input images. The RGB-only reconstruction is treated as candidate geometry, which can then be checked and corrected using estimated depth.

\subsection{Monocular Depth Estimation}
Monocular depth estimation predicts a dense depth map from a single RGB image. It is attractive for practical applications because it does not require stereo images or depth sensors. However, the problem is ill-posed. A single image cannot fully determine metric scale because different 3D scenes may project to similar 2D images. Recent work on scale ambiguity in monocular depth also emphasizes that metric depth from one image is under-constrained by perspective projection \cite{rsa_depth}.

Large-scale depth models such as \da{} improve monocular depth estimation through strong pretrained encoders and large training corpora. \da{} provides robust depth predictions and includes metric-depth variants obtained by fine-tuning pretrained encoders with metric depth labels \cite{depthanything_project,depthanything_metric}. This makes it a suitable initialization for the project. The fine-tuning stage uses RGB-D data as supervision so that the depth estimator adapts to indoor scenes and the reconstruction evaluation protocol.

\subsection{Depth-Assisted 3D Reconstruction}
Depth maps provide strong geometric information for 3D reconstruction. If measured depth and camera poses are available, a point cloud can be constructed by back-projecting valid depth pixels into 3D. However, this assumes that the user has a depth sensor and camera geometry at inference time. This assumption conflicts with the RGB-only deployment goal.

An intermediate solution is to use predicted depth instead of measured depth. Predicted depth is imperfect, but it can still provide useful geometric priors. In this project, predicted depth does not replace the multi-view backbone. Instead, it is used as a correction signal for candidate geometry. This design keeps the multi-view reasoning of \mvdp{} while using learned depth priors to reduce wrong-depth errors.

\subsection{Project Positioning}
This project does not train a new reconstruction backbone from scratch. Instead, it builds a structured pipeline on top of modern components. \mvdp{} provides candidate geometry from sparse RGB views, while the fine-tuned depth estimator provides a per-image metric-depth prior. The main contribution is the experimental setting, the depth fine-tuning process, and the correction module: using RGB-D data during development while keeping the final inference contract RGB-only.

\section{Model Architectures Used in the Project}
This section describes the two main model components used in the pipeline: \mvdp{} and \da{} Metric Indoor. It is placed before the dataset section so that the reader can understand what each model receives, what it outputs, and how it contributes to the final system.

\subsection{MV-DUSt3R+ Backbone}
\mvdp{} is a feed-forward sparse-view scene reconstruction model. Its input is a set of RGB images. Its output is a set of pixel-aligned 3D pointmaps and associated confidence information. Compared with pairwise DUSt3R-style reconstruction, \mvdp{} is designed to reason over multiple input views in one stage. It uses cross-reference-view reasoning to reduce sensitivity to the selected reference view and to improve stability in sparse-view settings.

In this project, \mvdp{} is used only as a frozen or pretrained reconstruction backbone. The project does not claim to modify the \mvdp{} architecture. Instead, \mvdp{} produces the RGB-only candidate point cloud. In the target RGB-only pipeline, the same \mvdp{} reconstruction is also used to recover camera geometry, namely estimated camera intrinsics and poses, from its predicted pointmaps by the pose/intrinsic recovery procedure described by Tang et al. \cite{mvdust3r_paper}. The proposed method then uses fine-tuned estimated depth and this recovered camera geometry to adjust the candidate point cloud.

\subsection{Depth Anything V2 Metric Indoor}
The depth estimator is initialized from \da{} Metric Indoor. This model predicts a dense metric depth map from a single RGB image. The pretrained checkpoint already provides useful indoor depth priors, but the project fine-tunes it on the available RGB-D data so that it better matches the dataset distribution and the reconstruction pipeline.

At inference time, the depth estimator receives each sparse RGB input view independently and predicts an estimated depth map. These estimated depth maps are then used as source-depth anchors for point-cloud correction. Because the depth is predicted from RGB, and the target camera geometry is recovered from the RGB-only \mvdp{} output, the final conceptual pipeline satisfies the RGB-only input contract.

\section{Problem Formulation}
Let a sparse group contain \(N\) RGB views:
\[
\mathcal{I}=\{I_1,I_2,\ldots,I_N\}, \quad N\in\{3,4,5\}.
\]
The final inference-time input is only the RGB images. During development, the dataset also provides measured depth maps and camera information that can be used for supervision, diagnostics, and evaluation:
\[
\mathcal{D}=\{D_1,D_2,\ldots,D_N\}, \quad
\mathcal{K}=\{K_1,K_2,\ldots,K_N\}, \quad
\mathcal{T}=\{T_1,T_2,\ldots,T_N\}.
\]
The measured depth maps \(\mathcal{D}\) are not used as final inference inputs. They are used to fine-tune the depth estimator and to evaluate reconstruction quality. The dataset camera intrinsics and poses, \(\mathcal{K}\) and \(\mathcal{T}\), are treated as reference camera geometry. In the final RGB-only formulation, the correction module should use camera geometry recovered from the \mvdp{} output:
\[
\hat{\mathcal{K}}=\{\hat{K}_1,\hat{K}_2,\ldots,\hat{K}_N\}, \quad
\hat{\mathcal{T}}=\{\hat{T}_1,\hat{T}_2,\ldots,\hat{T}_N\}.
\]
The hat symbol means ``estimated'', so \(\hat{K}_i\) and \(\hat{T}_i\) are not ground-truth calibration values provided to the deployed system; they are recovered from RGB-only multi-view reconstruction.

Here, \(K_i\) is the reference intrinsic calibration matrix of camera view \(i\), while \(\hat{K}_i\) is the estimated intrinsic matrix used by the target RGB-only pipeline:
\[
K_i =
\begin{bmatrix}
f_{x,i} & 0 & c_{x,i}\\
0 & f_{y,i} & c_{y,i}\\
0 & 0 & 1
\end{bmatrix}.
\]
The estimated matrix \(\hat{K}_i\) has the same form, but its entries are recovered by the pipeline instead of read from the dataset. The focal lengths \(f_{x,i}, f_{y,i}\) convert normalized camera coordinates to pixel units, while \(c_{x,i}, c_{y,i}\) are the principal-point coordinates. Therefore, \(\hat{K}_i^{-1}[u,v,1]^T\) converts an image pixel \((u,v)\) into a camera-ray direction in the local camera frame. This ray vector is a direction vector and is not required to have unit length.

\(T_i\) is the reference camera pose for view \(i\), represented as a homogeneous camera-to-world transform. The target pipeline uses the estimated version \(\hat{T}_i\):
\[
T_i =
\begin{bmatrix}
R_i & t_i\\
0 & 1
\end{bmatrix},
\quad R_i\in\mathbb{R}^{3\times3},\quad t_i\in\mathbb{R}^{3}.
\]
The estimated pose \(\hat{T}_i\) has the same block structure. The rotation \(R_i\) gives the camera orientation in the common world frame, and the translation \(t_i\) gives the camera center/location in that frame. In short, \(\hat{K}_i\) tells how a 2D pixel becomes a 3D viewing ray, while \(\hat{T}_i\) tells where that ray lies in the shared 3D coordinate system. Pose and intrinsic recovery alone do not determine depth: they define the ray, while the estimated depth \(\hat{D}_i(u,v)\) chooses a concrete point on that ray.

The \mvdp{} backbone predicts candidate points and provides the information used to recover camera geometry:
\[
P_{\mathrm{mv}},\hat{\mathcal{K}},\hat{\mathcal{T}} = f_{\mathrm{mv}}(\mathcal{I}).
\]
The fine-tuned depth estimator predicts depth maps from RGB:
\[
\hat{D}_i = f_{\mathrm{depth}}(I_i).
\]
The proposed correction module produces the final point cloud:
\[
P_{\mathrm{corr}} = C(P_{\mathrm{mv}}, \hat{\mathcal{D}}, \hat{\mathcal{K}}, \hat{\mathcal{T}}).
\]
Historical diagnostic runs may use the dataset \(K_i,T_i\) to isolate the effect of estimated depth. The target method, however, replaces measured source depth with estimated depth and replaces externally supplied camera geometry with \mvdp{}-recovered camera geometry.

\section{Proposed Method}
\subsection{Pipeline Overview}
The proposed pipeline has three stages:
\begin{enumerate}[leftmargin=1.2cm]
    \item \textbf{RGB-only candidate reconstruction and camera recovery.} Sparse RGB views are passed into \mvdp{} to obtain candidate 3D points, confidence scores, and recovered camera geometry \((\hat{K}_i,\hat{T}_i)\).
    \item \textbf{Monocular estimated depth.} Each input RGB image is passed through the fine-tuned \da{} Metric Indoor estimator to predict a depth map.
    \item \textbf{Estimated-depth correction.} Candidate points are compared with points back-projected from estimated depth using the recovered camera geometry. Points with large residuals are moved toward the estimated-depth anchor.
\end{enumerate}

This design is intentionally conservative. It does not replace multi-view reconstruction with monocular depth alone. Instead, depth is used as a correction signal for the multi-view candidate geometry. The role of \(\hat{K}_i\) and \(\hat{T}_i\) is to turn each estimated depth value into a 3D anchor in the same coordinate frame as the \mvdp{} candidates. These camera quantities define the viewing ray and coordinate frame; the estimated depth chooses the position of the point along that ray.

\subsection{Back-Projection from Estimated Depth}
For a source pixel \((u,v)\) in view \(i\), the estimated depth is \(\hat{z}=\hat{D}_i(u,v)\). First, the pixel is converted into a camera ray using the inverse estimated intrinsic matrix:
\[
d_i(u,v)=\hat{K}_i^{-1}
\begin{bmatrix}
u\\v\\1
\end{bmatrix}.
\]
Multiplying this ray by the estimated depth gives the 3D point in the local camera coordinate system:
\begin{equation}
\hat{X}^{\mathrm{cam}}_{\mathrm{src}}(u,v) =
\hat{z}\,d_i(u,v).
\end{equation}
This camera-coordinate point is then converted into homogeneous form and mapped into the common world coordinate system by the estimated camera pose \(\hat{T}_i\):
\begin{equation}
\begin{bmatrix}
\hat{X}^{\mathrm{world}}_{\mathrm{src}}(u,v)\\
1
\end{bmatrix}
=
\hat{T}_i
\begin{bmatrix}
\hat{X}^{\mathrm{cam}}_{\mathrm{src}}(u,v)\\
1
\end{bmatrix}.
\end{equation}
Thus, \(\hat{K}_i\) controls the direction of the source ray in the camera frame, \(\hat{D}_i\) controls how far along the ray the point lies, and \(\hat{T}_i\) places that point into the same 3D frame as the \mvdp{} candidate geometry.

In this notation, \((u,v)\) is a pixel coordinate, \(\hat{z}\) is the estimated metric depth at that pixel, \(d_i(u,v)\) is the corresponding camera ray direction, \(\hat{X}^{\mathrm{cam}}_{\mathrm{src}}\) is the estimated-depth point in the local camera coordinate system, and \(\hat{X}^{\mathrm{world}}_{\mathrm{src}}\) is the same point after transformation into the common world coordinate system. Without \(\hat{D}_i(u,v)\), the recovered pose and intrinsic parameters define only a ray, not a unique 3D point.

\subsection{Residual-Gated Correction}
Let \(X_{\mathrm{pred}}(u,v)\) be the \mvdp{} candidate point associated with the same source pixel. The residual between candidate geometry and estimated-depth geometry is:
\begin{equation}
r(u,v)=\left\|X_{\mathrm{pred}}(u,v)-\hat{X}^{\mathrm{world}}_{\mathrm{src}}(u,v)\right\|_2.
\end{equation}
The corrected point is:
\begin{equation}
X_{\mathrm{corr}}(u,v)=
\begin{cases}
(1-\alpha)X_{\mathrm{pred}}(u,v)+\alpha\hat{X}^{\mathrm{world}}_{\mathrm{src}}(u,v), & r(u,v)\geq\tau,\\
X_{\mathrm{pred}}(u,v), & r(u,v)<\tau.
\end{cases}
\end{equation}
Here, \(\tau\) is the correction threshold and \(\alpha\) is the correction weight. The intended final setting uses estimated depth from the fine-tuned model, not measured RGB-D source depth.

The residual gate has the following interpretation. \(X_{\mathrm{pred}}(u,v)\) is the \mvdp{} candidate point associated with pixel \((u,v)\). The term \(r(u,v)\) is the Euclidean distance between this candidate point and the estimated-depth anchor in the world frame. The norm \(\|\cdot\|_2\) is the standard 3D Euclidean norm. If \(r(u,v)<\tau\), the candidate is already close enough to the estimated-depth geometry and is kept unchanged. If \(r(u,v)\geq\tau\), the point is corrected by interpolation. \(\alpha=1\) moves the point fully to the estimated-depth anchor, \(\alpha=0\) keeps the \mvdp{} prediction, and values between 0 and 1 blend the two.

\section{Dataset and Experimental Setting}
The experiments use a Kaggle-hosted ScanNet-style indoor RGB-D dataset. In the Kaggle environment, the relevant data are discovered under the mounted \texttt{posed\_images} directory. The dataset is organized by scene. Each scene contains multiple posed RGB-D frames. A frame provides an RGB image, a measured depth map, reference camera intrinsics, and a reference camera pose. The RGB image is the visual input. The measured depth map is the sensor-style depth observation associated with the frame. The reference camera intrinsics \(K_i\) describe the projection geometry of view \(i\), and the reference camera pose \(T_i\) places that view in a common 3D coordinate system.

The target project formulation does not require these reference camera values as user-provided inputs at deployment time. Instead, \mvdp{} reconstructs candidate pointmaps from RGB and supports recovery of estimated intrinsics \(\hat{K}_i\) and estimated poses \(\hat{T}_i\). The reference \(K_i,T_i\) remain useful for controlled evaluation, sanity checks, and diagnostic experiments that isolate the effect of depth estimation from the effect of camera-geometry recovery.

The project uses the same data source in two different ways. First, for depth-estimator fine-tuning, the data are treated as a large frame-level RGB-D pool: RGB is the input and measured depth is the supervision target. Second, for 3D reconstruction evaluation, frames are grouped into sparse-view scene-level samples: a group contains only 3, 4, or 5 RGB views from the same scene, and the reconstruction system must produce a 3D point cloud from those sparse views.

\subsection{Sparse-View Group Construction}
A sparse-view group is the basic 3D reconstruction sample. All views in one group come from the same scene. The group contains \(N\in\{3,4,5\}\) selected RGB frames. These RGB frames are passed to \mvdp{} to obtain candidate pointmaps and recovered camera geometry. For correction methods, each source pixel can also be associated with a depth-derived 3D anchor by back-projecting either measured source depth or estimated source depth. In the target RGB-only method, estimated depth is back-projected through \(\hat{K}_i\) and \(\hat{T}_i\). In oracle or diagnostic RGB-D runs, measured source depth may be back-projected through reference \(K_i\) and \(T_i\). For fair point-cloud comparison, each group is evaluated using a fixed point budget; the Run 30 configuration uses at most 3500 candidate points per group.

\subsection{Sparse-View Selection Protocol}
View selection is part of the controlled evaluation protocol. The project does not solve automatic active view selection; instead, it constructs deterministic sparse-view groups and reuses exactly the same groups for all compared methods. This is important because RGB-only \mvdp{}, direct backprojection, measured-depth correction, pretrained-depth correction, and fine-tuned-depth correction must receive the same visual evidence. Therefore, differences in the reported metrics come from the reconstruction method, not from giving one method an easier set of input frames.

For each scene, the group manifest enumerates three view counts, \(N=3\), \(N=4\), and \(N=5\). For each view count, it constructs two view-selection policies:
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{Hybrid policy:} this policy chooses frames that keep moderate local overlap while still covering a wider camera trajectory than a very short temporal window. In the implementation, it uses fixed frame-index patterns within the first part of the scene sequence, for example a compact but not adjacent set of frames for each \(N\). This policy is intended to avoid both extremes: nearly identical neighboring views and very distant views with too little overlap.
    \item \textbf{Diversity-aware policy:} this policy selects spatially diverse camera positions. It starts from an initial frame and then repeatedly adds the frame whose camera center is farthest from the already selected set. This creates wider-baseline groups and stresses sparse-view reconstruction under lower overlap.
\end{itemize}

The selected image names are saved in the group manifest as the fixed input definition for that group. If a selection policy accidentally produces duplicate frames, the implementation replaces missing unique views with additional frames from the same scene. This guarantees that a requested 3-view, 4-view, or 5-view group actually contains the requested number of unique RGB inputs.

The evaluation then treats \texttt{scene\_id + num\_views + view\_policy} as a stable group key. For example, a group key such as \texttt{scene0012\_00\_4\_diversity\_aware} means that the scene is \texttt{scene0012\_00}, the input contains four RGB frames, and the frames were selected by the diversity-aware policy. When the group cap is unlimited, all constructed validation/test group keys are evaluated. When a positive cap is used for a pilot run, groups are sampled in a balanced way across scenes, view counts, and policies.

This design makes the ablation study cleaner. View selection is controlled and shared, while the method under test changes. The report therefore evaluates reconstruction robustness under fixed sparse-view inputs; it does not claim to learn or optimize the camera trajectory itself.

\subsection{Use of Measured Depth}
Measured depth has three different roles, and the report keeps them separate:
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{Depth supervision:} Run 37 uses measured depth as the training target for the monocular depth estimator.
    \item \textbf{RGB-D reference setting:} Run 30 uses measured source depth directly at inference time. This is a valid RGB-D setting, but it is not RGB-only.
    \item \textbf{Evaluation proxy:} the reconstruction evaluator builds a proxy reference point cloud from the available depth maps and camera geometry. This is useful for controlled comparison, but it is not an independent laser scan or official mesh benchmark.
\end{itemize}

The target final setting is different from the Run 30 RGB-D reference: it uses RGB images as input, lets \mvdp{} provide both candidate geometry and recovered camera geometry \((\hat{K}_i,\hat{T}_i)\), predicts depth with the fine-tuned depth estimator, back-projects the estimated depth using \(\hat{K}_i\) and \(\hat{T}_i\), and then applies the same style of correction to the \mvdp{} candidate geometry.

\subsection{Coverage Terminology and Benchmark Boundary}
The report distinguishes three terms:
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{All-scene discovery:} the script scans the mounted Kaggle dataset and discovers all scenes available to that run.
    \item \textbf{All-group metric evaluation:} after scenes are discovered, all constructed sparse-view groups are evaluated when the group cap is set to unlimited.
    \item \textbf{Official benchmark:} an official ScanNet or ScanNet++ benchmark would require the official split, official target representation, official evaluation protocol, and independent benchmark submission or reproduction. This project does not claim such a result.
\end{itemize}

Therefore, the reported numbers are controlled project metrics on a ScanNet-style Kaggle RGB-D dataset. They are appropriate for comparing the project ablations under the same evaluator, but they should not be presented as official full ScanNet or ScanNet++ benchmark scores.

\section{Evaluation Metrics}
\subsection{Depth Estimation Metrics}
Let \(D\) be the measured depth map and \(\hat{D}\) be the predicted depth map over valid pixels \(\Omega\). The depth metrics are:
\begin{align}
\mathrm{AbsRel} &= \frac{1}{|\Omega|}\sum_{p\in\Omega}\frac{|D(p)-\hat{D}(p)|}{D(p)},\\
\mathrm{MAE} &= \frac{1}{|\Omega|}\sum_{p\in\Omega}|D(p)-\hat{D}(p)|,\\
\mathrm{RMSE} &= \sqrt{\frac{1}{|\Omega|}\sum_{p\in\Omega}\left(D(p)-\hat{D}(p)\right)^2}.
\end{align}
The \(\delta_1\) accuracy is the fraction of pixels satisfying:
\begin{equation}
\max\left(\frac{\hat{D}(p)}{D(p)},\frac{D(p)}{\hat{D}(p)}\right)<1.25.
\end{equation}
Here, \(p\) denotes a valid image pixel, \(\Omega\) is the set of pixels whose measured depth is valid, \(D(p)\) is the measured depth at pixel \(p\), and \(\hat{D}(p)\) is the predicted depth at the same pixel. AbsRel measures relative depth error, so a 10 cm error is penalized more strongly for a nearby 50 cm point than for a distant 5 m point. MAE measures the average absolute metric error in meters. RMSE also measures metric error in meters, but it squares the error before averaging and is therefore more sensitive to large mistakes. \(\delta_1\) measures the percentage of valid pixels whose predicted depth is within a multiplicative factor of 1.25 from the measured depth. Lower AbsRel, MAE, and RMSE are better, while higher \(\delta_1\) is better.

\subsection{Point-Cloud Reconstruction Metrics}
Let \(P\) be the predicted point cloud and \(G\) be the reference point cloud. A point \(p\in P\) is one predicted 3D point, a point \(g\in G\) is one reference 3D point, and \(|P|\), \(|G|\) are the numbers of points in the two clouds. The nearest-neighbor operator \(\min_{g\in G}\|p-g\|_2\) finds the closest reference point to \(p\). Accuracy is the average nearest-neighbor distance from prediction to reference:
\begin{equation}
\mathrm{Accuracy}=\frac{1}{|P|}\sum_{p\in P}\min_{g\in G}\|p-g\|_2.
\end{equation}
Completeness is the average nearest-neighbor distance from reference to prediction:
\begin{equation}
\mathrm{Completeness}=\frac{1}{|G|}\sum_{g\in G}\min_{p\in P}\|g-p\|_2.
\end{equation}
Accuracy answers: ``how far are the predicted points from the reference?'' Completeness answers: ``how well does the prediction cover the reference?'' Both are distances, so lower is better.

Precision and recall are computed at a fixed metric threshold \(\tau_m\). In this project \(\tau_m=0.05\,\mathrm{m}\) for the main point-cloud evaluation:
\begin{align}
\mathrm{Precision} &= \frac{|\{p\in P:\min_{g\in G}\|p-g\|_2 \leq \tau_m\}|}{|P|},\\
\mathrm{Recall} &= \frac{|\{g\in G:\min_{p\in P}\|g-p\|_2 \leq \tau_m\}|}{|G|}.
\end{align}
Precision measures what fraction of predicted points are close enough to the reference. Recall measures what fraction of reference points are recovered by the prediction. F-score is:
\begin{equation}
F_1=\frac{2\cdot \mathrm{Precision}\cdot \mathrm{Recall}}{\mathrm{Precision}+\mathrm{Recall}}.
\end{equation}
Chamfer distance is:
\begin{equation}
\mathrm{Chamfer}=\mathrm{Accuracy}+\mathrm{Completeness}.
\end{equation}

Chamfer is lower when both the prediction-to-reference and reference-to-prediction distances are small. F-score is higher when both precision and recall are high.

For shape-level analysis, the project also reports Normalized Distance (ND) and the DAc@0.2 metric on selected qualitative groups. Before computing these metrics, both point clouds are center-normalized and scale-normalized. This removes global translation and scale differences so that the metric focuses more on shape agreement. ND is the average normalized nearest-neighbor distance, so lower ND is better. DAc@0.2 is the fraction of normalized points whose nearest-neighbor distance is at most 0.2, so higher DAc@0.2 is better. These normalized metrics should not be interpreted as absolute metric-pose evaluation.

\subsection{Ablation Study}
The ablation study answers three questions. First, comparing RGB-only \mvdp{} with pretrained-depth correction tests whether off-the-shelf monocular depth helps without task adaptation. Second, comparing pretrained-depth correction with fine-tuned-depth correction tests whether fine-tuning on RGB-D training data improves reconstruction. Third, comparing fine-tuned-depth correction with direct estimated-depth backprojection tests whether \mvdp{} still contributes useful multi-view geometry beyond monocular depth.

The updated ablation set is:
\begin{enumerate}[leftmargin=1.2cm]
    \item \textbf{Main:} \mvdp{} candidate geometry + recovered camera geometry + fine-tuned estimated-depth correction.
    \item \textbf{Ablation 1:} direct 3D backprojection from fine-tuned estimated depth, without \mvdp{} candidate geometry.
    \item \textbf{Ablation 2:} \mvdp{} candidate geometry + pretrained estimated-depth correction, without depth-estimator fine-tuning.
    \item \textbf{Ablation 3:} RGB-only \mvdp{} candidate point cloud, without any depth correction.
\end{enumerate}

This analysis is important because the proposed pipeline is not simply a depth-estimation project. It is a reconstruction pipeline that uses estimated depth to correct candidate multi-view geometry.

\subsection{Qualitative Analysis}
Qualitative results should show reconstructed point clouds side by side. For each selected scene group, the report should include the input RGB views, the RGB-only \mvdp{} point cloud, the direct estimated-depth point cloud, and the final corrected point cloud using fine-tuned estimated depth.

Successful cases are expected to show fewer floating points, better-aligned surfaces, and more stable geometry in ambiguous regions. Failure cases should also be reported, especially scenes with severe occlusion, repeated furniture, reflective surfaces, or inaccurate estimated depth.

\section{Discussion}
The proposed project is motivated by deployability. A system that requires measured depth at inference time can be accurate, but it is limited to users with specialized sensors. A system that only requires RGB images is easier to deploy because most cameras produce RGB images by default. Therefore, this project uses RGB-D data for training and evaluation while keeping the final inference input RGB-only.

This design also changes the interpretation of the dataset. The depth maps are not ignored. They are used as supervision for the depth estimator and as reference information for reconstruction evaluation. The final system then applies the learned depth knowledge to RGB-only inputs.

The expected benefit over RGB-only \mvdp{} is geometric stability. \mvdp{} provides multi-view candidate geometry but may still predict wrong depth in sparse-view settings. The fine-tuned depth estimator provides a per-image geometric prior. When estimated depth is reliable, the correction module can move candidate points toward more plausible metric positions. When estimated depth is unreliable, the correction should be weakened or rejected. This motivates future work on confidence-aware depth correction.

The second important factor is camera-geometry recovery. In the target RGB-only pipeline, the correction anchor depends on \(\hat{K}_i\), \(\hat{T}_i\), and \(\hat{D}_i\). If the recovered camera pose or intrinsic matrix is inaccurate, even a good depth estimate can be back-projected to the wrong 3D position. Therefore, diagnostic runs using reference \(K_i,T_i\) are useful for isolating depth quality, but they should not be confused with the final RGB-only camera setting.

The main limitation is that monocular depth is still imperfect. Fine-tuning reduces domain mismatch, but it does not remove all ambiguity. The depth model may still fail on unusual layouts, transparent objects, reflective surfaces, and scenes whose scale distribution differs from the training data. Camera-geometry recovery can also introduce errors in low-overlap or ambiguous views. Therefore, final claims should remain limited to the controlled sparse-view RGB-only setting and should not be presented as an official ScanNet or ScanNet++ benchmark unless the official protocol is implemented.

\section{Conclusion}
This project studies sparse-view RGB-only 3D scene reconstruction from a small number of ordinary 2D images. The motivation is practical: most everyday images do not include measured depth, and requiring a depth sensor would reduce deployability. The project therefore uses measured RGB-D data for supervision and evaluation, but not as an inference-time input.

The proposed pipeline combines \mvdp{} with a fine-tuned monocular depth estimator. \mvdp{} produces candidate multi-view geometry and recovered camera geometry from sparse RGB views, while the depth estimator predicts pseudo-depth maps from the same RGB inputs. The estimated-depth correction module back-projects those depth maps using the recovered camera intrinsics and poses, then refines candidate geometry to reduce wrong-depth errors and improve point-cloud quality.

The report defines an evaluation framework for this setting. Depth quality is measured using monocular depth metrics, while 3D reconstruction quality is measured using point-cloud metrics such as accuracy, completeness, precision, recall, F-score, and Chamfer distance. The main comparisons are RGB-only \mvdp{}, direct estimated-depth backprojection, pretrained-depth correction, and fine-tuned-depth correction. The final fine-tuned method should only be selected if it improves reconstruction metrics while preserving RGB-only inference.

Future work should complete the fine-tuned-depth reconstruction rerun under the updated camera-geometry protocol, compare it with the three ablations, add confidence-aware correction, and test the method on more diverse real RGB image sets. The long-term goal is a deployable reconstruction system that can produce useful 3D scene geometry from only a few ordinary 2D images.
